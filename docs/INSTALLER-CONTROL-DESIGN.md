# StandWatch: контроль стенду за installer

Актуальний стан реалізації, завершені перевірки, відомі нюанси та наступні
кроки зведено в [`IMPLEMENTATION-STATUS.md`](IMPLEMENTATION-STATUS.md).

Статус документа: UX погоджено; 14.09.2026 реалізовано перший read-only етап і
перевірено на Poruch QA. Backup, restore та deploy ще не реалізовані й не
запускалися.

Пілотний стенд: `Poruch QA`, `10.0.31.88`. На етапі проєктування та read-only
валідації сервер не змінювати. `RCC DEV` у пілот не включати.

## 1. Мета

StandWatch повинен уміти порівняти фактичний стан контейнерної групи на стенді з
точним складом відповідного installer і підготувати цілісний план переходу до
цього стану.

Installer задає бажаний стан одразу для всього свого складу. У режимі контролю
за installer нормальною операцією є оновлення всього manifest, а не ручний вибір
кожного сервісу окремо.

## 2. Режими

Режим задається для кожної контейнерної групи, а не обов'язково для всього
сервера.

### 2.1 Ручний

- версіями сервісів керують окремо;
- StandWatch може показувати Git/CI та доступні теги;
- розбіжність з installer не рахується і не блимає в UI;
- окремі сервіси можна готувати до ручного deploy.

### 2.2 За інсталятором

- до контейнерної групи прив'язаний installer-репозиторій;
- за ціль обирається tag installer або branch installer на конкретному commit;
- увесь manifest є цільовим станом групи;
- StandWatch показує всі відмінності сервісів, конфігів і керованих файлів;
- план охоплює весь installer; невирішена відповідність блокує виконання.

Якщо різні групи одного сервера мають різні режими, загальний режим сервера в UI
показується як `Змішаний`.

## 3. Кілька installer на одному сервері

На `Yetu QA` та подібних серверах може бути кілька окремих installer-
репозиторіїв. Наявне групування контейнерів на борді використовується як межа
відповідальності installer.

Installer-репозиторії задаються вручну в окремому менеджері. Структура каталогу:

`проєкт / банк → installer-репозиторії → прикріплені сервери`.

Кожен installer має назву, GitLab URL або `group/project` і шлях до manifest.
При додаванні сервера користувач обирає наявний проєкт/банк або створює новий.
У плані оновлення URL більше не вводиться: доступні лише installer з проєкту,
до якого прикріплений сервер.

Сервери в менеджері обираються компактною випадайкою з пошуком і галочками.
Один проєкт може містити кілька installer і кілька серверів.

Для кожної контейнерної групи зберігається окрема прив'язка:

- назва групи;
- GitLab path/ID installer-репозиторію;
- шлях до manifest у репозиторії;
- installation root на сервері, наприклад `/usr/local/rscore`;
- режим групи;
- обраний tag або `branch + commit`;
- правила дозволених локальних override.

Стабільна ідентичність прив'язки:

`GitLab project + manifest path + installation root`.

Самого локального шляху на сервері недостатньо. Якщо два installer заявляють
один і той самий сервіс, StandWatch показує конфлікт власності й нічого не
вирішує автоматично.

Installation root задається окремо для комбінації
`server + Docker Compose group + installer`. Спочатку StandWatch намагається
отримати `com.docker.compose.project.working_dir` і
`com.docker.compose.project.config_files`, потім перевіряє знайдені compose-файли.
Якщо labels відсутні або неоднозначні, користувач указує абсолютний шлях вручну.

## 4. Вибір цільового стану

### 4.1 Tag installer

Tag є незмінним посиланням на конкретний manifest. StandWatch зберігає:

- tag;
- commit, на який він указує;
- checksum отриманого manifest;
- час отримання.

### 4.2 Branch installer

Назва branch сама по собі не є цільовим станом, оскільки HEAD рухається.
Користувач:

1. обирає branch installer;
2. за замовчуванням отримує останній commit;
3. за потреби обирає один із попередніх commit;
4. бачить коротке preview змін manifest між вибраним і попереднім commit;
5. зберігає точний `branch + commit SHA + manifest checksum`.

Preview commit повинно показувати зміни складу, наприклад:

```text
dev @ 651820af

vpo-portal       1.4.1-dev.108 → 1.4.1-dev.110
vpo-service      1.9.2-dev.893 → 1.9.2-dev.900
report-service   1.4.0-dev.149 → 1.4.1-dev.150
+ configuration-service
- legacy-importer
```

У користувацькому UI не використовувати слово `baseline`. Назва дії:
`Зберегти цільовий стан`.

## 5. UI

Порівняння не повинно відкриватися центральною modal поверх борда.

- справа відкривається закріплена панель;
- борд сервісів стискається та зсувається вліво;
- затемнення фону немає;
- панель можна згорнути та, за можливості, змінювати її ширину;
- вибір рядка справа підсвічує відповідну картку сервісу зліва.

У ручному режимі installer-warning не показується. У режимі `За інсталятором`
заголовок контейнерної групи містить компактний статус, наприклад:

```text
VPO · installer dev@651820af · 3 відмінності
Retail · installer tag 6.4.0 · відповідає
X5 · ручний
```

Права панель має вкладки:

`Огляд | Сервіси | Конфіги | План`.

### 5.1 Блок цілі

Цільовий стан повинен бути головним візуальним акцентом, а не лише колонкою в
таблиці:

```text
ЦІЛЬОВИЙ СТАН

Poruch Installer
tag poruch-2026.09.14-rc.3

17 сервісів · 14 змін
3 конфіги · 1 відхилення
2 відповідності треба підтвердити
```

### 5.2 Вибір елементів

У режимі `За інсталятором` звичайні checkbox біля кожного сервісу не потрібні.
У план автоматично входить увесь manifest.

Виключення допускається лише як явний override з обов'язковою причиною. Після
цього група лишається позначеною як така, що свідомо не відповідає installer.

## 6. Конфіги й керовані файли

Installer повинен описувати не лише images, а й керовані файли та правила їх
перевірки.

Потрібно розрізняти:

- versioned YAML/JSON та scripts — checksum або нормалізоване порівняння;
- `.env` — schema, обов'язкові ключі й типи без показу secret values;
- дозволені локальні override — не помилка;
- невідомі локальні файли — `unmanaged`;
- файли, зміна яких потребує restart;
- конфіги, пов'язані з міграцією БД.

Для керованого файла manifest має задавати щонайменше:

- шлях відносно installation root;
- джерело/template;
- checksum або спосіб semantic validation;
- ownership і mode, якщо вони значущі;
- дозволені локальні поля;
- restart/migration impact.

Окремо треба погодити, чи installer-репозиторії містять готові конфіги для
конкретного стенду, чи шаблони, які доповнюються локальними значеннями.

## 7. Етапи операції

### 7.1 Сформувати план

Read-only операція:

- зберегти точний цільовий installer ref;
- зіставити весь manifest зі стендом;
- визначити сервіси, конфіги, БД, volumes і директорії;
- побудувати порядок оновлення;
- оцінити downtime, backup size та вільне місце;
- показати блокери й невирішені відповідності.

### 7.2 Підготувати оновлення та точку відновлення

Це вже операція зі станом. Вона створює backup поточного стенду й лише після
успішної перевірки розблоковує виконання плану.

### 7.3 Виконати план

Доступне лише коли:

- ціль не змінилась;
- manifest checksum збігається;
- немає невирішених відповідностей;
- preflight успішний;
- точка відновлення створена й перевірена.

## 8. Backup через SSH на локальний комп'ютер

На стендах мало вільного місця, тому backup потрібно передавати потоком через
наявне SSH-з'єднання без створення повної проміжної копії на сервері.

Потік:

`server command stdout → SSH → local .part file → validation → final file`.

Локальна структура restore point:

```text
backups/
  Poruch_QA/
    2026-09-14_163000/
      restore-point.json
      databases/
      directories/
      volumes/
      configs/
      container-state.json
      checksums.sha256
```

Правила:

- кожну БД, volume і директорію пакувати окремо;
- спочатку записувати `.part`;
- перевіряти checksum та читабельність архіву;
- при обриві SSH не дозволяти оновлення;
- до старту перевіряти вільне місце на локальному диску;
- шлях backup робити налаштовуваним, default — `StandWatch/backups`;
- секретні конфіги та DB dump захищати ACL і, бажано, шифруванням;
- визначити retention і ручне очищення старих restore point.

Замість копії контейнера зазвичай достатньо зберегти image digest і container/
compose metadata, якщо потрібний image гарантовано лишається в registry. Якщо
такої гарантії немає, `docker save` також передається потоком локально.

Для БД основним backup є консистентний `pg_dump`/`mysqldump`, а не архівування
активного DB volume. Статичні volumes можна стрімити без зупинки; volumes з
активним записом потребують quiesce, короткої зупинки сервісу або спеціального
snapshot-механізму.

## 9. Технічний fingerprint — прибрано з UI

Зараз StandWatch збирає:

- імена hashed `.js`/`.css` assets із головної web-сторінки;
- HTTP `Last-Modified` головної сторінки;
- SHA-256 відповіді `/swagger/v1/swagger.json`.

Це евристичний технічний відбиток. Він допомагає помітити, що фактичний web або
API-контракт змінився, навіть якщо metadata контейнера не пояснює зміну. Він не
визначає версію, installer, commit або коректність deploy.

Рішення від 15.09.2026: не показувати цей сигнал у борді або installer-плані.
Дані можуть залишатися у scan-моделі для технічної діагностики, але користувацький
UI їх не відображає.

## 10. `Є новіша версія`: tag проти branch

Поточна реалізація для розгорнутого чистого semver-тега `X.Y.Z` переглядає
доступні чисті semver-теги registry та показує найбільший із них. Це саме пошук
новішого tag, але нинішній текст у UI не пояснює джерело й може помилково
виглядати як рекомендація оновлення.

Потрібно показувати різні сигнали окремо:

- `Доступний новіший release tag: 6.4.0`;
- `У гілці dev є новіша збірка: 1.4.1-dev.110`;
- `У гілці є 3 commit, які ще не зібрані`;
- `Installer вимагає: 6.4.0`.

Не можна автоматично називати найбільший semver правильною ціллю. Наприклад,
перехід `2.1.5 → 3.2.0` може бути major upgrade, який цей стенд не повинен
отримувати. У режимі `За інсталятором` єдина рекомендована ціль береться з
manifest. У ручному режимі StandWatch лише повідомляє про доступні теги.

Перед реалізацією треба погодити policy для ручного режиму:

- показувати всі новіші теги чи лише ту саму major/minor release line;
- як відрізняти release, prerelease і branch-build tags;
- чи враховувати лише успішні TeamCity builds;
- як поводитися з тегами без Git/CI підтвердження.

## 11. Пілотна валідація на Poruch QA

Порядок пілота:

1. Read-only знайти installer-репозиторій Poruch і його manifest.
2. Визначити контейнерну групу, installation root і керовані шляхи.
3. Для tag отримати незмінний commit/checksum manifest.
4. Для branch показати останні commit і preview зміни складу.
5. Зіставити всі manifest services із 17 сервісами збереженого scan.
6. Окремо перевірити aliases на кшталт `portal → vpo-portal` і
   `report-service → vpo-report-service` через image/commit, а не лише назву.
7. Побудувати read-only звіт сервісів і конфігів.
8. Визначити DB/volume/directory backup scope та очікуваний розмір.
9. Показати план користувачу. Нічого на сервері не змінювати.
10. Backup stream, restore test і deploy дозволяти лише після окремого
    погодження.

## 12. Реалізований read-only етап (14.09.2026)

- для кожної контейнерної групи зберігається окремий режим `Ручний` або
  `Installer · контроль цільового стану`;
- installer обирається як окремий GitLab-репозиторій;
- tag фіксується точним commit, а branch — конкретним commit із HEAD за
  замовчуванням;
- склад із compose-файлів `home/*.yml` читається атомарно, без ручного вибору
  окремих сервісів;
- правий dock зсуває борд і показує цільовий склад, різниці та проблеми;
- індикатор на борді з'являється лише для груп із режимом installer;
- `Сформувати план` виконує тільки read-only SHA-256 звірку керованих текстових
  файлів через SSH. Секрети, `.env`, ключі та бінарні файли не читаються;
- технічний fingerprint web/backend прибрано з користувацького UI;
- окремий ручний каталог групує installer та сервери за проєктом/банком;
- загальний напис `є новіша версія` уточнено до `новіший release tag`.

Фактичний результат пілота для `Poruch QA / rscore / vpo/installer / dev /
b4bc5579`:

- installer: 18 сервісів, `home` 5, `scripts` 5, `volumes/config` 44;
- зі стендом збігаються 13 сервісів, змін потребують 4, уваги потребує 1;
- безпечно порівняно 40 файлів: 30 однакових, 10 відрізняються, 0 відсутніх;
- 14 потенційно секретних або непорівнюваних файлів проігноровано;
- жодних команд оновлення, backup або зміни сервера не виконувалось.

### Backend каталогу та автовиявлення (15.09.2026)

- каталог `проєкт/банк → installer → сервери` зберігається у
  `data/installer-catalog.json`, а не лише у браузері;
- наявні `installerGroups` автоматично мігруються в каталог без повторного
  введення;
- installation root зберігається в точній прив'язці контейнерної групи;
- read-only endpoint через SSH читає Docker Compose labels `project`,
  `project.working_dir` і `project.config_files`;
- Compose working directory нормалізується до кореня installer з урахуванням
  папки складу (`/usr/local/rscore/home` + `home` → `/usr/local/rscore`);
- Poruch QA: автоматично визначено `rscore → /usr/local/rscore`;
- Yetu QA: автоматично визначено `retail → /usr/local/retail`,
  `rscore → /usr/local/rscore`, `x5 → /usr/local/x5` та окрему DB-групу
  `rscore-db → /usr/local/rscore/test/db_postgres`;
- усі операції цього етапу є read-only для віддалених серверів.

### Backup preflight (15.09.2026)

- `Сформувати план` паралельно з checksum конфігів виконує read-only inventory:
  `df`, `du` для `home/scripts/volumes` і `docker inspect` для контейнерів та
  mounts;
- до scope входять не лише контейнери вибраної compose-групи, а й окремі
  compose-проєкти, чий `working_dir` лежить під тим самим installation root;
- БД поки лише виявляються як кандидати за image/name; dump, архівація і зупинка
  контейнерів не виконуються;
- Poruch QA `/usr/local/rscore`: 20 контейнерів у групах `rscore`, `database`,
  `test`; 55 mounts; `volumes` близько 3.24 GB; виявлено PostgreSQL
  `rscore-postgresql` з bind mount `/usr/local/rscore/volumes/postgresql/pgdata`;
- на цьому етапі сервер не змінюється і локальні backup-файли не створюються.

### Локальний snapshot плану (15.09.2026)

- після успішної checksum-звірки й backup preflight план атомарно зберігається у
  `data/plans/<timestamp>_<server>_<group>.json`;
- snapshot містить точний installer commit/checksum, цільові версії сервісів,
  відмінні/відсутні конфіги та backup inventory;
- початкові стани: `status: read-only-draft`, `backup: not-created`,
  `deploy: blocked-until-backup`;
- це ще не точка відновлення: жодні дані із сервера не копіюються, поки окремо
  не реалізовано й не запущено потоковий backup.

## 13. Відкриті питання

- Формат і місце manifest у кожному installer-репозиторії.
- Звідки брати перелік БД та спосіб їх backup/restore.
- Які volumes активні, статичні або взагалі не потребують backup.
- Чи потрібна друга копія backup поза локальним комп'ютером.
- Допустимий downtime під час створення консистентної точки відновлення.
- Шифрування, retention і максимальний обсяг локальних backup.
- Правила semantic comparison конфігів і дозволених override.
- Policy для індикатора новішого release tag у ручному режимі.

## 14. GitLab-зміни після останньої збірки (15.09.2026)

Виправлено помилкову базу порівняння. Лічильник `треба збілдити` не можна
рахувати від образу, який зараз розгорнутий на стенді: стенд може відставати від
вже готових TeamCity build і тоді UI помилково покаже вже зібрані commit як
незбілджені.

Джерела розділено:

- `стенд відстає` — build/commit розгорнутого образу проти останнього успішного

## 15. Перегляд сформованого плану

- Великий результат планування не вбудовується під таблицю installer-звірки.
- Після формування доступна окрема кнопка `Переглянути поточний план`; вона
  відкриває модалку з сервісними змінами, конфігами та backup preflight.
- План можна вважати поточним лише доки tags сервісів відповідної compose-групи
  збігаються зі станом, збереженим у `data/plans/*.json`.
- Якщо сервер змінився, старий план не приховується, але явно маркується
  застарілим і перелічує сервіси, які розійшлися.
- Банер відмінностей на board є прямим переходом до installer-панелі з уже
  вибраним фільтром `Зміни`.

## 16. Формування локальної точки відновлення

Точка відновлення створюється лише для поточного незміненого plan snapshot.
Backend повторно звіряє tags із кешем scan і відмовляється працювати, якщо план
застарів.

Потік артефактів:

1. `docker inspect` compose-групи → локальний `containers.json`.
2. `tar -czf - home scripts volumes` → SSH stdout → локальний
   `stand-files.tar.gz`.
3. Для кожного PostgreSQL-контейнера `pg_dumpall` → SSH stdout → локальний
   `database/<container>.sql.gz`.
4. Локальна перевірка gzip, SHA-256 і запис `restore-point.json`.

Живий PostgreSQL data directory не вважається валідним backup. Якщо його bind
mount лежить усередині installation root, він виключається з файлового tar;
відновлення БД має виконуватися з `pg_dumpall`.

Статус `verified` означає, що локальні артефакти записані та пройшли перевірку
цілісності. Це ще не означає, що автоматичний restore перевірено. До реалізації
restore workflow deploy залишається заблокованим.
