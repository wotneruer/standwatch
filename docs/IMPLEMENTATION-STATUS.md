# StandWatch — стан реалізації та нюанси

Дата зрізу: **16.09.2026**  
Остання тестова portable-збірка: **2026.09.15.13**  
Пілот installer-контролю: **Poruch QA (`10.0.31.88`)**

Першу локальну точку відновлення Poruch QA успішно створено та перевірено
**16.09.2026**. Фактичні артефакти й сценарій майбутнього destructive restore
зафіксовано в `PORUCH-RESTORE-DRILL.md`.

## 1. Що вже покрито

### 1.1 Portable desktop-застосунок

- StandWatch збирається в один portable `.exe` і сам розгортає runtime у папку
  `StandWatch` поруч із запущеним файлом.
- Дані зберігаються локально біля EXE: `data/config.env`, `servers.json`, кеші,
  каталог installer і плани.
- Оновлення payload не повинно перезаписувати користувацькі дані.
- Є окрема збірка з поточними даними для продовження дебагу без повторного
  введення серверів і токенів.
- Перевірено чистий запуск і запуск із перенесеними даними.

Нюанс: portable не треба запускати двічі одночасно. Другий процес може спробувати
оновити файли, які вже використовує запущений StandWatch. Перед оновленням слід
натиснути `✕ Вийти`, а потім один раз запустити новий EXE.

### 1.2 SSH та додавання серверів

- При першому налаштуванні можна вибрати існуючий ключ моніторингу або створити
  `standwatch_monitoring`.
- Окремо задається робочий приватний ключ першого входу.
- Команда встановлення public key одразу містить правильний шлях у `ssh -i`.
- Зайва кнопка прирівнювання робочого ключа до ключа StandWatch прибрана.
- Новий сервер після додавання стає поточним, без помилкового повідомлення про
  дубль і без необхідності вручну переходити на нього.
- Сервер під час створення прикріплюється до наявного проєкту/банку або створює
  новий.

### 1.3 Scan стендів, registry, GitLab і TeamCity

- Через SSH читаються контейнери, точні image tags, digest, OCI/rscore labels,
  branch, build і commit.
- Registry перевіряється за реальним namespace кожного образу, а не лише одним
  глобальним шляхом.
- GitLab-проєкти шукаються автоматично за image name і підтверджуються commit.
- Підтримуються специфічні назви, а не лише VPO. Наприклад,
  `vpo-report-service` коректно знаходить `vpo/services/report-service`.
- TeamCity build type для невідомих сервісів підбирається за build number,
  image/namespace/branch similarity; неоднозначні збіги відкидаються.
- Для RCC Mission Care залишена точна відома прив'язка build configuration.

### 1.4 Коректне визначення «треба збілдити»

Початково GitLab порівнювався з commit образу, розгорнутого на стенді. Це давало
хибний результат: якщо стенд мав Web `#120`, а TeamCity вже успішно зібрав
`#122`, 18 уже зібраних commit показувалися як незбілджені.

Логіку розділено:

- **стенд відстає**: build/commit на сервері порівнюється з останнім успішним
  завершеним TeamCity build відповідної гілки;
- **треба збілдити**: GitLab compare виконується від revision останнього
  успішного TeamCity build до HEAD гілки;
- TeamCity `Pending Changes` не використовується як джерело істини, оскільки
  може оновлюватися із затримкою;
- якщо TeamCity revision не знайдено, fallback до commit образу явно позначається
  як непідтверджений.

Контрольна перевірка RCC QA:

- `rcc-mission-care-web`: TC `#122`, commit `60434352`, GitLab ahead `0`;
- `rcc-mission-care-service`: стенд `#204`, TC `#205`, commit `3e75fdfe`,
  GitLab ahead `0`; окремо видно, що стенд відстає на одну збірку.

Важливий нюанс: `rcc-mission-care-web` і `rcc-mission-care-service` мають різні
GitLab-проєкти й TeamCity configurations. Саме їх плутання спочатку ускладнило
діагностику 18 commit.

### 1.5 Ручний та installer-режими

Для кожної Docker Compose-групи окремо задається режим:

- `Ручний` — StandWatch моніторить стан, але не нав'язує installer target;
- `Installer · контроль цільового стану` — ціль визначається installer manifest.

У installer-режимі:

- можна вибрати tag installer;
- можна вибрати branch і зафіксувати конкретний commit, за замовчуванням HEAD;
- зберігаються точний commit і checksum manifest;
- до плану входить весь склад installer, а не вручну вибрані сервіси;
- показується коротке preview змін commit;
- сервер не змінюється під час звірки.

### 1.6 Каталог проєктів / банків та installer-репозиторіїв

- Є окремий менеджер `проєкт/банк → installer-репозиторії → сервери`.
- В одному проєкті може бути кілька різних installer-репозиторіїв.
- Сервери прикріплюються через dropdown із checkbox.
- Каталог зберігається у `data/installer-catalog.json`, а не лише в браузері.
- Старі `installerGroups` автоматично мігрують у каталог.
- Для installer задається папка складу manifest, наприклад `home`.

### 1.7 Installation root і автоматичне виявлення

- Для кожної зв'язки `сервер + compose-група + installer` зберігається точний
  installation root.
- Root можна ввести вручну або визначити через Docker Compose labels:
  `project`, `project.working_dir`, `project.config_files`.
- Working directory нормалізується з урахуванням manifest root:
  `/usr/local/rscore/home + home → /usr/local/rscore`.

Перевірено:

- Poruch QA: `rscore → /usr/local/rscore`;
- Yetu QA: `retail → /usr/local/retail`, `rscore → /usr/local/rscore`,
  `x5 → /usr/local/x5`, окрема DB-група під `rscore/test/db_postgres`.

### 1.8 Read-only план і конфігурації

- Installer snapshot читає compose-файли `home/*.yml` і весь керований склад
  `home`, `scripts`, `volumes/config`.
- Сервіси installer зіставляються з контейнерами стенду.
- Керовані текстові файли порівнюються через SHA-256 по SSH.
- `.env`, private keys, certificates, secret-файли та бінарні файли не читаються
  і не порівнюються побайтово.
- Показуються `відповідає`, `змінити`, `перевірити`, а також відсутні й зайві
  позиції.

Пілот Poruch QA на першому зафіксованому installer commit:

- installer: 18 сервісів;
- збігалося 13, змін потребували 4, уваги — 1;
- порівняно 40 безпечних файлів: 30 однакових, 10 відрізнялися;
- 14 секретних або непорівнюваних файлів проігноровано.

### 1.9 Backup preflight

`Сформувати план` тепер виконує read-only inventory:

- `df` для вільного місця;
- `du` для `home`, `scripts`, `volumes`;
- `docker inspect` для контейнерів і mounts;
- пошук DB-кандидатів за image/name;
- включення сусідніх compose-проєктів, якщо їх `working_dir` лежить під тим самим
  installation root.

Poruch QA `/usr/local/rscore`:

- 20 контейнерів у групах `rscore`, `database`, `test`;
- 55 mounts;
- `volumes` приблизно 3.24 GB;
- знайдено PostgreSQL `rscore-postgresql`;
- bind mount БД: `/usr/local/rscore/volumes/postgresql/pgdata`;
- на момент перевірки на серверній файловій системі було близько 19.4 GB вільно.

Preflight нічого не архівує і не змінює на сервері.

### 1.10 Збереження draft-плану

- Після checksum-звірки та preflight створюється локальний атомарний snapshot у
  `data/plans/<timestamp>_<server>_<group>.json`.
- Він містить installer commit/checksum, цільові версії, різницю конфігів і
  backup inventory.
- Початкові стани: `read-only-draft`, `backup: not-created`,
  `deploy: blocked-until-backup`.
- `.part` використовується під час запису, щоб не залишати готовим обірваний
  JSON-файл.

### 1.11 UI, який уже виправлено

- Installer відкривається як правий dock і зсуває board, а не перекриває його.
- Клік поза звичайними модалками закриває їх.
- Верхня навігація серверів замінена компактним selector.
- Налаштування цілі у правій панелі згортані; після збереження лишається короткий
  рядок `група · tag/commit · root`.
- Таблиця відповідностей отримала основну висоту панелі.
- Footer із кнопками не повинен виходити за межі dock.
- Сформований план більше не займає низ правого dock: після формування з'являється
  кнопка `Переглянути поточний план`, а повний звіт відкривається в окремій
  прокручуваній модалці.
- Останній план перевіряється проти поточного scan. Якщо хоча б один tag на
  сервері змінився, кнопка стає `⚠ План застарів`, а модалка показує розбіжності.
- Клік на банері `Відмінності від installer` відкриває праву панель одразу з
  активним фільтром `Зміни`.
- Кнопку `Завантажити звіт` прибрано як зайву; footer переносить кнопки на
  наступний рядок на вузькій панелі й більше не обрізає `Закрити`.
- Другорядні кнопки у footer та модалці плану отримали контрастний фон, виразну
  рамку й hover-стан, щоб не зливатися з панеллю.
- У правій таблиці та модалці плану джерела розрізняються стабільними кольорами:
  синій `● Сервер зараз`, фіолетовий `◆ Installer target`; стани конфігів мають
  зелені/жовті/червоні badges.

### 1.12 Локальна точка відновлення

- У модалці поточного плану явно розділено `DB-контейнер виявлено` і
  `DB dump створено`: саме виявлення більше не виглядає як готовий backup.
- Для незміненого поточного плану доступна кнопка `Створити локальний backup`.
- Дані передаються потоком через SSH одразу на локальний ПК; великий проміжний
  архів на сервері не створюється.
- `home`, `scripts`, `volumes` записуються у `stand-files.tar.gz`.
- Для PostgreSQL перевіряються `psql` і `pg_dumpall`, оцінюється розмір баз і
  створюється окремий `database/<container>.sql.gz` через `pg_dumpall`.
- Шляхи живого PostgreSQL data mount усередині installation root виключаються
  з файлового tar: джерелом відновлення БД є консистентний SQL dump.
- Перед стартом перевіряється запас місця на локальному диску.
- Для кожного артефакту обчислюється SHA-256; gzip повністю перечитується для
  перевірки цілісності. Результат фіксується у `restore-point.json`.
- На Linux автоматично використовується багатопотоковий `pigz -1`, якщо він
  доступний; на Poruch QA він уже встановлений.
- UI показує етап, приблизний відсоток, переданий обсяг і поточну швидкість.
- Runtime-логи та всі `volumes/*/pgdata` виключаються з файлового tar. PostgreSQL
  відновлюється лише з окремого консистентного `pg_dumpall`.
- Backup блокується, якщо план застарів, DB engine не підтримується, немає
  `pg_dumpall`, не визначився розмір БД або бракує локального місця.
- Restore поки не автоматизовано. Навіть після успішного backup deploy має стан
  `blocked-until-restore-workflow`.
- План повторно використовується, доки tags контейнерів не змінилися. За наявності
  актуального плану кнопка має назву `Переформувати план` і просить підтвердження.
- Потоковий writer використовує єдиний stdout pipeline: лічильник не читає SSH
  stdout паралельно з файловим writer. Це усуває пошкодження великих gzip-файлів.
- `Повторити backup` для стану `failed` повторно використовує каталог спроби й
  перед стартом прибирає лише пошкоджені app-generated `.part/.tar.gz/.sql.gz`,
  щоб невдалі багатогігабайтні архіви не накопичувались.
- Коротке повідомлення після збереження цілі зникає автоматично.
- `фінгерпринт web/backend` прибрано з користувацького UI.
- Напис `є новіша версія` уточнено до `новіший release tag`.

## 3. Оновлення 16.09 — installer scope та перевірка restore

- Прив'язка installer тепер фіксує `scopeFiles`: конкретні compose-файли для
  зв'язки `сервер + Docker-група + installer`. UI автоматично пропонує файли за
  перетином образів із контейнерами групи, але дозволяє змінити вибір вручну.
- Звірка й загальний індикатор використовують лише цей scope, тому `retail` і
  `rscore` одного сервера не повинні змішуватися.
- Installer snapshot читає `.env` у корені репозиторію та в manifest root,
  розкриває `${VAR}`, `${VAR:-default}` та фіксує нерозкриті змінні як проблему,
  а не як вигаданий тег.
- Збереження installer-каталогу серіалізовано; нормалізована відповідь backend
  зливається у поточні об'єкти без stale-reference проблеми.
- Після verified backup доступний недеструктивний `Перевірити відновлення БД`:
  StandWatch перевіряє SHA-256, створює ізольований PostgreSQL без портів і без
  робочих volumes, потоково відновлює `pg_dumpall`, порівнює roles, databases,
  extensions і перелік таблиць із живою БД та видаляє лише створені ним
  тимчасові container/volume.
- Діагностика restore-test зберігається біля backup:
  `restore-test.jsonl`, `restore-test-result.json`,
  `restore-test-container.log`. Лише повний успіх дає статус `restore-tested`;
  destructive drill до цього заблокований.
- Фактичний Poruch restore-test плану `20260916080531886_poruch_qa_rscore`
  пройшов успішно: `postgres:14.5`, roles/databases/extensions/tables збіглися,
  тимчасові Docker-ресурси після тесту прибрані.

## 4. Що потрібно погодити перед destructive drill

1. Локальний каталог backup за замовчуванням і мінімальний запас вільного місця.
2. Retention: скільки restore points зберігати та хто їх видаляє.
3. Чи потрібне шифрування DB dump і конфігів із секретами.
4. PostgreSQL strategy: `pg_dump`, `pg_dumpall`, окремі databases/roles та спосіб
   перевірки dump.
5. Які volumes є статичними, а які активно змінюються.
6. Чи достатньо DB dump для PostgreSQL, чи додатково потрібна копія `pgdata`.
   Архівувати активний `pgdata` без зупинки небезпечно.
7. Які контейнери треба quiesce/зупинити та який downtime допустимий.
8. Чи потрібно виконувати `docker save`, якщо registry не гарантує retention
   старих image digest.
9. Як валідувати restore: лише checksum/читабельність архіву чи тестове
   відновлення в окремому контейнері.
10. Які локальні конфігураційні override дозволено зберігати після оновлення.

## 5. Наступний етап

1. Запустити недеструктивний restore-test на свіжому backup Poruch QA.
2. Зафіксувати очікуваний container inventory, health endpoints і startup
   критерії для `rscore`.
3. Створити другий свіжий verified backup безпосередньо перед drill.
4. Додати окрему операцію destructive drill з подвійним підтвердженням,
   поетапним журналом і зупинкою при першій невідповідності.
5. Лише після успішного drill додати явну операцію виконання installer-плану
   installer-плану.
9. Після deploy пересканувати сервер і звірити фактичний стан із зафіксованим
   installer checksum/target.

## 6. Відомі обмеження та правила безпеки

- Найбільший semver у registry — лише інформаційний `новіший release tag`, а не
  автоматична рекомендація оновлення.
- У installer-режимі єдиною рекомендованою ціллю є зафіксований manifest.
- TeamCity Pending Changes не є надійною основою для GitLab ahead.
- Якщо немає точного Git/CI підтвердження, UI має показувати невизначеність.
- Backup, deploy і rollback не можна вважати готовими лише через наявність
  read-only плану.
- На поточному етапі StandWatch не повинен автоматично змінювати Poruch QA під
  час installer-звірки.

## 7. Що перевірити у наступній збірці

1. Після `Зберегти цільовий стан` блок налаштувань згортається.
2. Нижні кнопки завжди доступні й не виходять за межі dock.
3. Фільтри `Усі / Зміни / Проблеми` працюють без прокрутки всієї сторінки.
4. Після `Сформувати план` великий звіт не з'являється внизу dock; доступна
   кнопка `Переглянути поточний план`.
5. Кнопка відкриває модалку з сервісами, конфігами та backup preflight.
6. Якщо після формування змінився tag сервісу, план позначається застарілим.
7. Клік `Відмінності від installer` одразу відкриває фільтр `Зміни`.
8. Після формування з'являється новий JSON у `data/plans`.
9. Після перезапуску зберігаються installer, tag/commit та installation root.
10. Жоден контейнер, файл або БД на сервері не змінюється.
11. У `Backup і відновлення` до запуску чітко написано, що DB лише виявлена.
12. `Створити локальний backup` створює каталог `StandWatch/data/backups/<plan-id>`.
13. У ньому є `stand-files.tar.gz`, `containers.json`, `restore-point.json` і
    `database/rscore-postgresql.sql.gz` для Poruch QA.
14. Після успіху стан змінюється на `✓ Локальний backup створено і перевірено`.
